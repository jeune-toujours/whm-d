# WHM-02 · Ручная инвентаризация ячеек

Источник: [актуальное ТЗ от 01.11.2026](https://app.notion.com/p/40b75fc615c881b1a8accf49e9f3806a). Оно отменяет месячную очередь из старого backlog. Никаких inventory_period, dueAt, cron или автоматического создания проверок.

## План реализации и критерии

1. **INV-01/02:** каталог ячеек с поиском, складом/зоной и множественным выбором. Manager/admin запускают одну операцию; пустой/невалидный выбор отклоняется. Idempotency-Key, транзакционные advisory locks и уникальный индекс активной ячейки защищают повторы/параллельные старты.
2. **Данные:** в текущем проекте нет общей Operations: Orders описывает только intake/return и содержит клиентские/платёжные обязательные поля. Добавляем InventorySessions и InventorySessionCells через additive migration; существующие заказы не меняются.
3. **INV-03:** staff проверяет неизменяемый снимок содержимого каждой ячейки. Можно подтвердить соответствие, отметить отсутствующие вещи и добавить фактически обнаруженные коды, включая неизвестные. Сохраняются фактический список, missing/extra/wrong_cell, комментарий, исполнитель и время. Расхождение требует комментария.
4. **INV-04:** прогресс 0/N → N/N, история, отдельные результаты каждой ячейки. Итог completed или completed_with_discrepancies. Результаты закрытой ячейки нельзя перезаписывать; точный повтор своего запроса возвращает сохранённый результат.
5. **Регрессия:** unit сверки, DB integration прав/конфликтов/идемпотентности/параллельного завершения/immutable snapshot и отсутствия изменений размещения; браузерный сценарий три ячейки + мобильный экран; существующий полный складской flow.

## Принятые границы первой версии

- Ручной запуск и ручное подтверждение. Существующий камерный BarcodeField — необязательный способ добавить код, фото не обязательно.
- Нет назначения, дедлайнов, отмены или согласования расхождений: эти решения в ТЗ ещё открыты.
- Перемещения, владельцы и заказы не блокируются и не исправляются инвентаризацией. Учёт на момент проверки сохраняется отдельно; интерфейс предупреждает об отличии от снимка запуска.
- Ролевой охват совпадает с существующим backoffice: staff видит склады/ячейки; ограничений по конкретным зонам пока нет. Client не имеет доступа ни к custom API, ни к native Payload коллекциям.
- Технический предел одного запуска — 200 ячеек; каталог постраничный, выбор сохраняется между страницами. Это ограничение запроса, не правило периодичности/учёта. Снимок не обрезается лимитом страницы.

## API и состояние

- GET /api/v1/inventory/cells — каталог и занятость открытыми инвентаризациями.
- GET/POST /api/v1/inventory — история/очередь и ручной запуск.
- GET /api/v1/inventory/:id — снимки, прогресс, результаты.
- POST /api/v1/inventory/:id/cells/:checkID — окончательный результат ячейки, с Idempotency-Key.
- Sessions: in_progress → completed / completed_with_discrepancies. Session cells: pending → matched / discrepancy. Активная ячейка удерживается до завершения всей операции, затем доступна для нового запуска.
- Создание/изменение/удаление native Payload коллекций запрещено; все изменения через workflow с аудитом.

## Хранение и миграция

- `inventory-sessions`: номер, инициатор и имя на момент запуска, сводка складов, статус, счётчики, времена, ключ и хеш запроса.
- `inventory-session-cells`: адрес и штрихкод ячейки, склад/зона, неизменяемый expectedItems, фактические коды/распознанные предметы, расхождения, комментарий, исполнитель/время, учёт на момент проверки, checkKey/checkHash.
- `20261101_143058_manual_inventory` добавляет только таблицы, enum, связи и индексы. Существующие заказы, ячейки и вещи не пересоздаются.
- Дополнительный SQL-индекс `inventory_session_cells_active_cell_unique (cell_id) WHERE active = true` задаётся вручную в миграции: Payload schema не описывает partial unique index. Сохранять его при будущих миграциях; schema push по-прежнему запрещён.
- Ключи idempotency привязаны к пользователю. Точный повтор возвращает тот же результат, другое тело с тем же ключом отклоняется; другая проверка не может занять уже использованный ключ.
- При закрытии ячейки её данные окончательны. Общая операция закрывается при N/N; только тогда освобождаются все активные ячейки.

## Работа сотрудника

1. В админке открыть «Операции WHM → Инвентаризация».
2. Manager/admin: «Создать инвентаризацию», поиск и фильтры, отметить адреса, проверить список выбранных и запустить. Занятые ячейки ведут к уже открытой операции.
3. Warehouse/manager/admin: открыть операцию, сверить вещи с ожидаемым списком, снять отметки с отсутствующих. Для найденных дополнительных предметов ввести коды или использовать камеру рядом с полем. Сканировать ничего не обязательно.
4. При расхождении заполнить комментарий и сохранить проверку. Сохранённое подтверждение содержит имя, ссылку на пользователя для manager/admin и время.
5. После последней ячейки итог появляется в «История». Исправление размещения или учёта выполняется отдельно по принятым складским процессам.
