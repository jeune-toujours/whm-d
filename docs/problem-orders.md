# Проблемные заказы · WHM-01 · v0.1.6

Источник: [backlog встречи 18.10.2026](https://app.notion.com/p/40475fc615c881278c91db418f2e0863), WHM-01. Актуальное решение владельца 19.11.2026: фиксация сначала остаётся внутренней; клиент получает информацию после отдельного подтверждения кейса в админке. Согласование 2–3 сотрудниками не требуется.

## Как пользоваться

В админке: **Операции WHM → Проблемные заказы** (`/admin/warehouse/problems`). Либо в приёмке у вещи нажать «Зафиксировать повреждение при поступлении» — приёмка и вещь подставятся автоматически.

1. Выбрать текущую приёмку и вещь в её составе.
2. Описать повреждение, при необходимости добавить до пяти материалов (фото, видео, PDF; до 25 МБ каждый).
3. Отметить, что повреждение обнаружено при поступлении, и сохранить внутреннюю фиксацию. Запись и материалы видны только сотрудникам; обращения и клиентского события заказа ещё нет.
4. Менеджер или администратор открывает запись и нажимает «Подтвердить кейс и уведомить клиента».

При подтверждении одной транзакцией сохраняются подтвердивший сотрудник и время, материалы становятся доступны владельцу, создаются обращение с первым сообщением в поддержке и событие `damage_found` в истории заказа. В карточке вещи клиента появляется история повреждения с переходом в этот чат. Повтор подтверждения возвращает существующий кейс без новых сообщений, обращений или событий. Складской сотрудник фиксирует, но не публикует; менеджер/admin может выполнить оба шага самостоятельно.

Юридическая форма акта ещё не утверждена. Это операционная фиксация, без обозначения ТОРГ-2/ТОРГ-12 и без юридической подписи. Реальные SMS/email не отправляются. После подтверждения уведомление доставляется внутри личного кабинета.

Уточнение владельца 19.11.2026: продолжать без новых ключей S3. В staging задано `PROBLEM_EVIDENCE_ENABLED=false`: выбор файлов скрыт, API отклоняет новые вложения; текстовая фиксация и уведомление работают. После восстановления доступа к бакету включить флаг и проверить загрузку и чтение. CI проверяет полную ветку с приватным тестовым S3.

## Данные и ограничения

- `damage-reports` — неизменяемое описание и снимок вещи/номера заказа, автор фиксации, материалы, состояние `pending` / `published`, время и автор публикации, связь с обращением после подтверждения. На одну вещь в одной приёмке создаётся одна запись.
- `media.internalOnly` — серверный запрет клиентского чтения внутренних материалов. Новый модуль загружает файлы с этим флагом. При публикации снимает его только для материалов этого клиента; изоляция владельцев сохраняется. Клиент не может менять этот флаг. Приватность действует и для native API и прямого пути файла.
- `support-tickets` / `support-messages` — уведомление клиента и дальнейшая обычная переписка по проблеме.
- `order-events.damage_found` и поддержка создаются только при подтверждении; `audit-log` сохраняет и внутреннюю фиксацию, и публикацию.
- Запись доступна для вещей `expected` или `received` в текущей заявке на сдачу `created`/`received`. Повреждение после размещения — иной сценарий, его правила пока не согласованы.
- Фиксация не изменяет статус, ячейку, тариф, блокировки и оплату вещи. Компенсации, ответственность сторон и обязательность материалов не утверждены.
- Создание доступно активным `warehouse`, `manager`, `admin`; подтверждение — только `manager`, `admin`. Прямые create/update/delete через Payload закрыты всем. Клиентский API фильтрует `published` на сервере. Подтверждение существующей фиксации возможно и после продолжения складской операции.
- Публикация, доступ к материалам, сообщение клиенту, событие и аудит коммитятся одной PostgreSQL-транзакцией. Advisory locks предотвращают дубли при конкурирующих подтверждениях.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/problems` | Поиск, страницы, фильтр `state=pending/published/all` |
| `GET /api/v1/problems/context` | Текущие приёмки для выбора; поиск, страницы, фильтр `orderID` |
| `POST /api/v1/problems` | Внутренняя фиксация; обязательный `Idempotency-Key` |
| `GET /api/v1/problems/:id` | Карточка записи сотруднику |
| `POST /api/v1/problems/:id/publish` | `{confirmed:true}`; менеджер/admin; повтор безопасен |
| `GET /api/v1/items/:id/problems` | Только подтверждённые кейсы собственной вещи |

Миграция `20261119_145318_problem_confirmation` добавляет состояния, данные публикации и приватность медиа, делает связь с обращением необязательной до подтверждения. Записи v0.1.5 с уже созданным обращением остаются опубликованными, без повторных уведомлений. Миграция не приписывает им задним числом сотрудника, якобы нажавшего подтверждение. Миграции запускает новый образ при старте; schema push не используется.

Откат приложения на v0.1.5 при наличии внутренних фиксаций небезопасен: прежний API не фильтровал их по статусу. Для исправлений использовать совместимый образ или forward fix, не автоматический `migrate:down`.

## Проверки

`backend/tests/problems.integration.ts`: отсутствие клиентских сообщений/событий/истории до подтверждения, приватность файлов через native API и прямой путь, права ролей, защита CRUD, конкурентные подтверждения, отсутствие дублей и изменение доступности материалов только при публикации.

`scripts/problems-smoke.mjs` в `test:live`: внутренняя фиксация из приёмки, невидимость клиенту, отдельное подтверждение, создание чата, история вещи, поиск и ширины 320/390/1440 px. Staging проверяется без файлов, CI — с приватным S3.
