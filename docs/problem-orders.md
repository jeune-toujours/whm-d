# Проблемные заказы · WHM-01 · v0.1.5

Источник: [backlog встречи 18.10.2026](https://app.notion.com/p/40475fc615c881278c91db418f2e0863), пункт WHM-01. Уточнение владельца 19.11.2026: подтверждения несколькими сотрудниками не нужны. Запись сразу фиксируется одним сотрудником.

## Как пользоваться

В админке: **Операции WHM → Проблемные заказы** (`/admin/warehouse/problems`). Либо в приёмке у вещи нажать «Зафиксировать повреждение при поступлении» — приёмка и вещь подставятся автоматически.

1. Выбрать текущую приёмку и вещь в её составе.
2. Описать повреждение, при необходимости добавить до пяти материалов (фото, видео, PDF; до 25 МБ каждый).
3. Отметить, что повреждение обнаружено при поступлении, и сохранить.

Сразу сохраняются номер записи, описание, материалы, сотрудник и время, привязка к клиенту, вещи и приёмке. Клиент получает обращение с сообщением в своём разделе поддержки, а в карточке вещи видит историю повреждений. В истории заказа сохраняется событие `damage_found`. Повторная отправка того же запроса не создаёт второй акт или сообщение.

Юридическая форма акта ещё не утверждена. Это операционная фиксация, без обозначения ТОРГ-2/ТОРГ-12 и без юридической подписи. Реальные SMS/email не отправляются. Уведомление доставляется внутри личного кабинета. Согласования сотрудниками нет.

Уточнение владельца 19.11.2026: продолжать без новых ключей S3. В staging задано `PROBLEM_EVIDENCE_ENABLED=false`: выбор файлов скрыт, API отклоняет новые вложения; текстовая фиксация и уведомление работают. После восстановления доступа к бакету включить флаг и проверить загрузку и чтение. CI проверяет полную ветку с приватным тестовым S3.

## Данные и ограничения

- `damage-reports` — неизменяемые записи повреждений. Номер заказа и название вещи сохраняются снимком; отношения с `orders`, `storage-items`, `users`, `media` и `support-tickets` позволяют открыть первичные данные. На одну вещь в одной приёмке создаётся одна запись.
- `support-tickets` / `support-messages` — уведомление клиента и дальнейшая обычная переписка по проблеме.
- `order-events` — событие фиксации в истории заказа; `audit-log` — автор и перечень изменённых полей.
- Запись доступна для вещей `expected` или `received` в текущей заявке на сдачу `created`/`received`. Повреждение после размещения — иной сценарий, его правила пока не согласованы.
- Фиксация не изменяет статус, ячейку, тариф, блокировки и оплату вещи. Компенсации, ответственность сторон и обязательность материалов не утверждены.
- Создание доступно активным `warehouse`, `manager`, `admin` через специальный API. Прямые create/update/delete через Payload закрыты всем. Клиент видит только историю собственных вещей и свои обращения; внутреннюю коллекцию актов читать не может.
- Операция создания, сообщение клиенту, событие и аудит коммитятся одной PostgreSQL-транзакцией. Advisory locks и уникальные индексы предотвращают дубли при конкурирующих запросах.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/problems` | Поиск по номеру записи/заказа/вещи, 25 записей на страницу |
| `GET /api/v1/problems/context` | Текущие приёмки для выбора; поиск, страницы, фильтр `orderID` |
| `POST /api/v1/problems` | Фиксация; обязательный `Idempotency-Key` |
| `GET /api/v1/problems/:id` | Карточка записи сотруднику |
| `GET /api/v1/items/:id/problems` | История повреждений собственной вещи клиенту |

Миграция `20261119_135242_problem_orders` добавляет таблицу записей, связи медиа и индексы без изменения существующих данных. Миграции запускает новый образ при старте; schema push не используется.

## Проверки

Интеграционный сценарий `backend/tests/problems.integration.ts` проверяет права, владение вещами/материалами, конкурирующие повторы, неизменяемость, уведомление, историю и отсутствие изменения складского учёта. Браузерный сценарий `scripts/problems-smoke.mjs`, включённый в `test:live`, проверяет переход из приёмки, сохранение с материалом, поиск, клиентскую карточку и ширины 320/390/1440 px.
