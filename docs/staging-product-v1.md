# WHM: первая рабочая версия staging

Решение владельца от 4 октября 2026: все данные тестовые; реализуем SMS и оплату с симуляторами, внешние провайдеры пока не подключаем. Source of truth — [master plan в Notion](https://app.notion.com/p/3ef75fc615c881808c1fdcd5ffb69ea6). Production пока остаётся прежним frontend.

## Проверка продукта

Клиент: https://test-whm.pikman.studio. Тестовый аккаунт с готовыми вещами: **+7 999 000 00 01**. Для регистрации нового клиента используйте другой номер в диапазоне **+7 999 000 XX XX**. Шестизначный код приходит в тестовый SMS inbox на экране ввода кода. Коды не пишутся в логи и не сохраняются открытым текстом в challenge или Jobs.

1. Войти / зарегистрироваться, заполнить имя и фамилию.
2. Создать сдачу: выбрать каталог, количество, описание, способ и пожелание по времени передачи.
3. В симуляторе платежа выбрать отказ, затем успешную оплату. Сумма рассчитана сервером по каталогу; повторное подтверждение не создаёт второй платёж.
4. В Payload Admin пройти **Приёмку → Размещение**. Приёмка требует штрихкод, пломбу коробки и фото/видео. Размещение проверяет скан вещи, скан ячейки и вместимость.
5. В клиенте оформить возврат. Вещь резервируется сервером; две заявки на одну вещь одновременно запрещены.
6. В админке пройти **Подбор → Выдачу**: сканирование, фото/видео, подпись получателя и подтверждение передачи. Вещь переходит в `returned`, ячейка освобождается.
7. Проверить историю, карточку вещи с приватными материалами, платежи и квитанцию. Перезагрузка браузера сохраняет результат.
8. Создать обращение с вложением, ответить в админке и проверить переписку в клиенте.

Админка: `/admin`; процессы: `/admin/warehouse/receive`, `/place`, `/pick`, `/return`, `/support`. Используется текущий администратор. `warehouse` не имеет доступа к финансовым записям и переписке поддержки; `manager` и `admin` работают с обращениями. Клиентский и административный кабинеты используют общую cookie Payload: для одновременной проверки открывайте их в разных профилях браузера или приватном окне.

## Реальные данные и симуляторы

Svelte / JavaScript обращается в WHM API. Пользователи, вещи, заявки, резервирование, размещение, обращения, платежные метаданные, аудит и события сохраняются в Selectel PostgreSQL. Файлы загружаются в приватный Selectel S3; срок signed URL — 5 минут. Серверные проверки работают и через native REST Payload.

SMS: полный цикл challenge → очередь Payload Jobs → симуляция доставки → проверка → HttpOnly session. TTL 5 минут, максимум 5 проверок, cooldown 60 секунд, 3 запроса на телефон / 20 на IP за 15 минут. Смена номера имеет отдельный challenge, связанный с текущим клиентом; код входа не подходит для смены номера.

Платежи: создание `pending`, симуляция `failed` / `paid`, повторная попытка, защита от дублей и позднего отказа после успеха. Оплаченная отменённая тестовая сдача получает `refunded`; повторная отмена не создаёт новый возврат. Квитанция — JSON с фактической суммой/статусом, явно **не фискальный чек**. Карта симулируется фиксированными маскированными метаданными; PAN/CVV не запрашиваются.

Подписка: выбор тестового тарифа через оплату и серверная проверка лимита вещей; приостановка разрешена только без вещей и активных заявок. Это ограничение тестового сценария. Реальный календарь начислений, автосписания, финансовое распределение и сроки паузы не реализуются до утверждения правил. Отключение тестового аккаунта закрывает вход, сохраняя аудит; это не юридическая процедура удаления персональных данных.

Все записи каталога `testOnly=true`: восемь вариантов хранения, три подписки, восемь ячеек, один клиент и три начальные вещи. Seed идемпотентен, не очищает базу и не возвращает уже выданные тестовые вещи на склад.

## Явные тестовые допущения

- Платёж за сдачу равен сумме месячных цен вещей. Это тестовый сценарий, не утверждённая политика биллинга.
- Пожелание по дате/времени не резервирует реальную доставку. Курьер не назначается автоматически, контакты не выдумываются.
- Не создаём юридические акты, оферту и фискальные чеки. Фото, подпись и события хранят факты тестовой операции.
- МойСклад, настоящие SMS/PSP, email, доставки и автосписания не подключены. Технические обращения доступны в переписке backoffice; автоматическая отправка разработчикам по email пока отсутствует.
- Никаких иллюстраций и брендинга. Существующие темы и UI kit сохранены, в клиенте только Lucide. Фото появляются только после реальной загрузки в складском сценарии.

## Настройки и выпуск

Backend runtime: `APP_ENV=staging`, `SIMULATE_INTEGRATIONS=true`, `SEED_STAGING=true`, `DATABASE_PUSH=false`. Симуляция с другим APP_ENV запрещает запуск. `SEED_STAGING` запускает seed после миграций перед Next. `WHM_BUILD=1` не передаётся runtime.

Frontend build: `VITE_DEMO_MODE=false`, `VITE_API_URL=/api` (same origin). Исторический просмотр экранов остаётся доступен в отдельной сборке `VITE_DEMO_MODE=true`; live-продукт не использует localStorage для данных, только для темы.

Миграция `20261004_173013_operational_v1` расширяет foundation без сброса данных. Перед применением к production нужен отдельный релиз и отдельные production credentials. Откат кода не означает откат миграции; обратная миграция может удалить данные новых полей и требует отдельного решения.

Проверки: frontend check/build/test:flows; backend check/unit/build; GitHub CI — PostgreSQL 17 и временный приватный S3 для тестов, миграции дважды, точный Docker image, ownership, конкурирующие резервирования/размещения, платежные дубли, поддержка, native CRUD и браузерный проход всех четырёх складских операций. `npm run test:live` создаёт тестовые данные и требует изолированный staging / CI и административные credentials из env либо защищённого SSH-файла; секреты не печатаются.

Перед объявлением релиза успешным: Coolify `finished`, оба приложения `running:healthy`, HTTPS `/health`, `/release.json`, `/api/health`, `/api/ready` и одинаковый commit SHA; затем browser flow на опубликованном staging.
